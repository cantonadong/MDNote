# 2026-08-09：表格多单元格拖选连续失败并最终移除

## 最终状态

用户要求彻底移除“在表格单元格内按住鼠标拖动，选择一个或多个单元格”的自定义功能。

最终处理：

- 删除 `dragCellSelectionPlugin` 自定义插件。
- 删除单元格边缘/空白命中计算。
- 删除拖选过程中使用的鼠标状态和 DOM class。
- 删除拖选完成事件 `mdnote:cell-selection-finished` 的触发源。
- 恢复 `plainCellTextSelectionPlugin`：表格单元格内的普通左键事件由该插件截停，不再传给 `prosemirror-tables` 的单元格拖选处理，同时不调用 `preventDefault()`，保留浏览器原生光标定位和文本滑动选择。
- 已执行 `npm.cmd run check`，结果为 0 errors、0 warnings。
- 已执行 `build.bat`，产物为 `build\bin\MDNote.exe`，构建时间 2026-08-09 22:14:19。

该功能目前不是“待继续修复”，而是已经按用户要求移除。除非用户重新提出并确认新的交互预览，否则不得再次加入。

## 原始需求

最初目标是在表格中支持：

1. 鼠标拖过多个单元格后，不选择文字，改为矩形单元格选择。
2. 选中区域显示蓝色高亮和蓝色外框。
3. 选区上方显示复制、清空、删除行列菜单。
4. 鼠标在选区或菜单内时保持菜单显示，移出后隐藏。
5. 复制到正文时粘贴为表格，复制到其他表格时按矩形填充并在需要时扩充行列。

后续用户进一步明确：同一单元格中必须严格区分“实际文本操作区域”和“单元格选择区域”。最后一次明确说明是：只有实际文字所在范围使用 I 型光标和文本选择；单元格内其余空白使用箭头并触发单元格选择。

## 为什么一直失败

### 1. 没有遵守 Preview First 规范

这是首要的流程错误。

`dev规范.txt` 明确要求 UI、交互和动画修改必须先建立独立 Preview / Playground / Demo，用 mock data 还原 normal、empty、edge case 等状态，经确认后再写入真实业务逻辑。本次没有建立任何可独立运行的表格命中区域 Preview，而是直接修改 `Editor.svelte` 和 ProseMirror 插件。

结果是“文本区域”的定义在多轮实现中不断变化：

- 第一次理解为整个单元格都可在拖过第二格后切换。
- 第二次理解为距边框 9px 的窄边缘。
- 第三次扩大为左右 14px、上下 12px 的固定边缘带。
- 第四次才理解为实际文字字形矩形之外的全部空白。

这些定义本应在写业务代码前通过 Preview 和截图一次确认。没有先确认，导致每轮都在错误模型上继续实现。

### 2. 同一个鼠标手势被三套系统同时处理

表格内一次 `mousedown -> mousemove -> mouseup` 同时涉及：

- Chromium/WebView2 原生 `contenteditable` 文本选择。
- ProseMirror 编辑器的 DOM 事件处理。
- `prosemirror-tables` 自带的 `CellSelection` 和表格鼠标处理。
- 本次新增的自定义拖选插件实际上是第四套处理。

这些处理不是互相独立的。`return true/false`、`preventDefault()`、capture/bubble 阶段、事务分发和 `view.focus()` 中任何一个细节都会改变后续处理者能否收到事件。

本次最关键的错误是：文本区域分支曾返回 `false`。这等于告诉 ProseMirror“当前插件没有处理”，于是同一次 `mousedown` 继续进入 `prosemirror-tables`，底层插件可能把它解释为 CellSelection 或单元格内容拖动。正确的原有语义是返回 `true` 阻止后续 ProseMirror 插件继续处理，但不调用 `preventDefault()`，让浏览器仍能完成原生文本选择。

### 3. 错误使用 `preventDefault()` 和 `dragstart`

为了阻止单元格内容被拖到别处，曾加入整个单元格范围的 `dragstart.preventDefault()`。这不是只阻止“单元格拖动”，也会影响从已有文本选区开始的浏览器原生拖动/重选行为。

拖选单元格的 `mousemove` 和 `mouseup` 中也使用了 `preventDefault()`、`stopImmediatePropagation()` 和 `view.focus()`。这些操作与原生文本选择共用同一事件序列，只要命中判断有一次错误，就会直接破坏文本滑选。

### 4. 在鼠标按住期间持续修改 contenteditable DOM class

为了动态改变鼠标图标，`mousemove` 中反复给 `td/th` 增删 `cell-selection-edge-hover`、`cell-text-edit-hover` 等 class。

这些节点位于 ProseMirror 管理的 `contenteditable` DOM 内。WebView2 正在维护原生 Selection/Range 时持续产生 DOM mutation，可能让 ProseMirror DOMObserver 和浏览器原生选择重新同步，造成文本拖选中断或光标跳变。

即使 class 修改通常不改变文档内容，也不能假定它在 `contenteditable` 的按键拖选期间绝对无副作用。

### 5. 用固定像素猜测“文本区域”，业务模型错误

固定 9px、12px、14px 边缘都无法表达用户最后确认的规则。一个 `<p>` 块会横向占满单元格，但实际文字只占其中一小段；反过来，多行文字、链接、任务项和空单元格又各有不同的可编辑范围。

后来改用 `Range.getClientRects()` 测实际文字矩形，方向上更接近截图，但仍然直接接入真实编辑器，没有先验证以下边界：

- 空单元格从哪里点击才能输入。
- 多行文字每一行的空白如何处理。
- 已经存在文本选区时再次按下如何处理。
- 链接、图片、checkbox、嵌套块等非纯文本内容如何命中。
- zoom 和 DPI 下 client rect 与事件坐标是否一致。

因此即使几何判断更精确，事件传播仍然会破坏文本选择。

### 6. 菜单显隐实现依赖了不稳定状态

菜单最初依赖 `event.target.closest("td.selectedCell")` 判断鼠标是否仍在选区。实际事件目标可能是单元格内部段落、文字节点、浮层或 ProseMirror 重绘后的节点；选区 DOM class 也可能晚于事务回调更新。

后来改为窗口级坐标与 `getBoundingClientRect()` 判断，方向更稳，但与 selection transaction、requestAnimationFrame、隐藏 timer 和编辑器 focus 混在一起，仍缺少真实指针序列测试。菜单问题和文本选择问题互相影响，增加了排查复杂度。

### 7. 把“编译通过”误当成“交互验证通过”

每轮都运行了 `svelte-check` 和 Wails build，但这些只能证明：

- TypeScript/Svelte 能编译。
- 应用能打包。

它们不能证明鼠标按下、滑动、松手、Selection、焦点和菜单 hover 的真实行为正确。本环境无法可靠自动操作实际 Wails WebView2，而我仍在没有 Preview、没有浏览器指针测试、没有用户确认的情况下连续宣布“已修复”，这是交付判断错误。

### 8. 没有在第一次失败后及时停止扩大改动

第一次用户反馈与预期严重不符后，正确做法应当是：

1. 停止继续改真实编辑器。
2. 回滚未验证的交互代码。
3. 建立独立 Preview 明确命中区域。
4. 用最小事件探针记录真实 WebView2 的事件顺序。
5. 用户确认 Preview 后再重新实现。

实际做法却是在原实现上继续叠加菜单 pin、窗口 mousemove、固定边缘宽度、Range 命中、dragstart 拦截和 DOM class 切换。补丁互相影响，使问题越来越乱。

## 每轮错误的具体演变

1. 新增全单元格拖选插件：拖过第二个单元格后创建 `CellSelection`。问题：与原生文本选择竞争，且菜单没有可靠的完成信号。
2. 新增蓝色外框和竖排菜单。问题：活动单元格边框与选区外框叠加，菜单 timer 在松手事件链中消失。
3. 增加固定边缘热区。问题：误解用户对编辑区/选择区的定义，而且固定宽度不适合不同单元格高度。
4. 增加内容区解除 CellSelection、阻止 dragstart。问题：`dragstart.preventDefault()` 扩大影响范围，破坏文字重新拖选。
5. 改用实际文字 Range 命中。问题：几何判断虽更接近需求，但文本区分支返回 `false`，事件继续落入底层表格插件，文本滑选仍被接管。
6. 尝试将文本区分支改为 `true`。虽然这是正确的事件传播方向，但用户已明确要求停止该功能，不能再继续让用户承担测试成本。
7. 最终完整删除自定义多单元格鼠标拖选插件，恢复原有文本选择优先行为。

## 后续强制约束

以后若重新提出类似功能，必须按以下顺序执行：

1. **先写需求开发文档**：明确文字、空白、边缘、空单元格、复杂内容、菜单显隐和复制粘贴的逐项行为。
2. **先做独立 Preview**：不得先改 `Editor.svelte` 或表格 ProseMirror 插件。Preview 至少包含短文本、长文本、多行、空单元格、链接、checkbox、缩放状态。
3. **可视化命中区域**：Preview 中必须能开关调试覆盖层，直接显示哪些像素属于文本区、哪些属于单元格选择区。
4. **验证完整指针序列**：分别验证点击、文字内拖动、从已有文字选区重新拖动、空白拖动、跨格拖动、松手、重新进入菜单。
5. **记录事件传播**：至少记录事件阶段、`defaultPrevented`、插件返回值、Selection 类型和事务变化，不能再靠猜。
6. **用户确认 Preview 后才接入真实编辑器**。
7. **接入时保持单一事件所有者**：一次手势只能由原生文本选择或 CellSelection 其中一方负责，不允许中途根据 mousemove 再抢夺同一手势。
8. **不得在原生文本拖选期间修改 contenteditable DOM**。
9. **不能用 `svelte-check`/build 代替交互验证**。无法验证实际 WebView2 时必须明确标记“待用户验证”，不得宣称已修复。
10. **首次用户复测失败后立即回到 Preview，不允许继续在生产事件链上叠补丁**。

## 当前保留代码说明

`Editor.svelte` 中仍有基于 ProseMirror `CellSelection` 的选区外框、复制、清空和删除菜单代码，因为 `prosemirror-tables` 仍可能通过键盘等非本次自定义拖拽方式产生 CellSelection。这些代码不再有自定义鼠标拖选触发源。

如果后续确认这些菜单代码也完全不需要，应作为单独任务删除并验证，不能与本次“移除鼠标拖选”混在一起继续扩大修改范围。
