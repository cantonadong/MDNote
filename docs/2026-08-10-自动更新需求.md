# 自动更新需求与实现设计

## 用户流程

1. 每个本地自然日第一次启动 MDNote 时，后台请求 `cantonadong/MDNote` 的最新公开 GitHub Release。
2. 当前版本不低于云端版本、网络失败或 Release 没有可用的 `MDNote.exe` 时，不打扰用户。
3. 云端版本更高时，在后台下载 `MDNote.exe` 到当前程序目录的临时更新文件。
4. 下载完成后校验 GitHub Release 提供的 SHA-256（有摘要时必须一致）。
5. 校验成功后，左下角显示“已准备升级”，用户点击“升级并重启”后才退出当前程序。
6. 独立更新进程等待旧进程完全退出，替换当前 exe，启动新版本，并删除旧版本和临时更新文件。

## 状态与异常

- checking/downloading：完全后台运行，不显示提示。
- ready：显示左下角升级提示；允许“升级并重启”或“稍后”。
- 网络、API、下载、摘要或磁盘失败：本次静默结束，不影响编辑和启动。
- 下载中关闭应用：临时文件不能替换当前程序；下次检查可清理/重新下载。
- 无写入 exe 目录权限：不替换程序，不删除现有版本。
- 有未保存内容：点击升级时必须先走现有保存/关闭保护，不能直接丢弃编辑内容。

## 技术设计

- Go 后端负责每日检查、下载、SHA-256、暂存文件以及 Windows 进程替换。
- 使用 GitHub Releases API 的 `tag_name`、`assets[].browser_download_url` 和 `assets[].digest`。
- 版本使用数值段比较，兼容 `v1.5`、`1.5.1`，不使用字符串字典序。
- `config.ini` 保存上次成功完成检查的本地日期；请求未完成时不写日期，避免中断后整天不能重试。
- 后端通过 Wails event 向前端发布 ready 状态；前端只负责提示与用户确认。
- 新下载的 exe 以更新器模式启动，等待旧 PID 退出后完成复制和重启；正常单实例逻辑之前处理更新器参数。

## 验收用例

1. 同一天多次启动只请求一次；跨日首次启动重新检查。
2. `1.5` 对 `v1.5` 不升级，`1.5` 对 `v1.6` 升级，`1.10` 高于 `1.9`。
3. 下载前不显示 UI；完整下载且摘要正确后才显示提示。
4. 用户点“稍后”后本次隐藏，程序不重启。
5. 用户确认后旧进程退出、新 exe 替换并启动，旧 exe 与暂存文件最终删除。
6. 下载失败、摘要错误、资产缺失、目录不可写均保持当前 exe 可用。
7. 更新过程不删除或覆盖 `config.ini`、`syncstate.json` 和笔记目录。

## 回滚

前端提示组件与 Preview 独立；确认前不接入启动检查、下载和 exe 替换逻辑。生产接入可通过移除更新服务启动和事件监听完整关闭。
