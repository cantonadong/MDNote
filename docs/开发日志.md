## 踩过的坑

1. **`npm create tauri-app@latest -- --name X --identifier ...` 参数解析异常**：CLI 实际不支持 `--name` 选项（项目名是位置参数 `PROJECTNAME`），传入后被误当成目录名，生成了一个字面量叫 `--name` 的目录。修正：改用位置参数，`npx create-tauri-app@latest . --manager npm --template svelte-ts --identifier com.mdnote.app --yes --force`，用 `.` 直接在当前目录（已有 need.md 等文件，非空目录需加 `--force`）生成。
2. **联网失败重试**：首次 `rustup-init.exe` 下载 channel 元数据时报 `os error 10013`（防火墙尚未放行），按 `dev规范.txt` 规则新开一个 PowerShell 进程、等待 10 秒后重试，第二次直接成功（Rust 1.97.1 安装完成）。**结论：本机确实存在"同进程首次联网请求会被拒，需换新进程重试"的现象，后续联网操作若失败应默认走这个重试流程，不要反复在同一进程里重试。**
3. **MSVC 链接器被 Git 自带的 `link.exe` 覆盖**：`cargo build`（`tauri build --debug`）报 `error: linking with link.exe failed`，日志显示实际调用的是 GNU coreutils 的 `link`（"extra operand" 是 coreutils `link(1)` 的报错特征，不是 MSVC link 的报错格式）。根因：`D:\Program\Git\usr\bin\link.exe`（Git for Windows 自带的类 Unix `link` 命令）在 PATH 中排在 MSVC 的 `link.exe` 之前，rustc 调用 `link.exe` 时被错误解析到这个文件。
   **解决方案**：新建了可复用脚本 `scratchpad/msvc-env.ps1`，通过调用 `vcvarsall.bat x64` 抓取 `INCLUDE`/`LIB`/`PATH`（含正确的 MSVC `link.exe`、Windows SDK 路径）注入当前 PowerShell 进程环境变量，再把 `D:\Program\Rust\cargo\bin` 和 `D:\Program\nodejs` 前置到 PATH（因为 `beforeBuildCommand`/`beforeDevCommand` 需要跑 `npm run build`/`npm run dev`）。**之后所有涉及 `cargo build` / `tauri build` / `tauri dev` 的命令都要先 dot-source 这个脚本**，否则会再次被 Git 的 `link.exe` shadow。
   （未对用户级全局 PATH 做永久改动来解决此问题，避免影响 Git 在其他场景下的正常使用；只在构建所需的单次进程环境里生效。）

## 2026-07-23：改用 Go + Wails，一次性推进到可测试版本

用户要求把外壳/后端从 Tauri(Rust) 换成 Go 实现，优先保证 exe 体积、内存、CPU 尽可能小；并要求整体 UI 尽量还原 Notion 风格；并明确指示"除非遇到问题，否则一路做到可用测试版 exe 为止"，因此本次未按 `dev规范.txt` 的 Preview-First 流程逐步暂停确认，而是直接产出可运行 exe 供用户验收（后续如需，再回头补 Preview 环节）。

**技术选型**：Go + Wails v2（继续复用系统 WebView2，不内置 Chromium）。放弃"纯原生 Go GUI（Fyne/Gio）"方案，因为会丢失 Tiptap/ProseMirror 的 WYSIWYG 编辑能力，需要用户在两条路线间二选一时已确认选择 Wails。

**目录重构**：
- 删除 `src-tauri/`（Rust 后端）。
- 前端整体从仓库根目录搬到 `frontend/`（Wails 约定的前端目录），`package.json` 移除 `@tauri-apps/*` 依赖。
- 根目录新增 Go 模块：`main.go`（窗口/embed 配置）、`app.go`（对话框 + 设置绑定方法）、`fsops.go`（目录树 CRUD）、`settings.go`（便携配置读写）、`wails.json`。
- `svelte.config.js` 的 `adapter-static` 输出目录改为 `dist`（匹配 `main.go` 里 `//go:embed all:frontend/dist`）。

**已实现功能**（一次性写完，非分步 Preview）：文件系统绑定（`ListDir/ReadFile/WriteFile/CreateEntry/RenameEntry/DeleteEntry/MoveEntry`，均校验落在根目录内）、设置持久化、左栏目录树（懒加载 + 右键菜单 + 拖拽移动 + markdown-only 过滤 + 隐藏 `.md` 后缀）、多标签（脏标记/中键关闭/关闭确认）、顶部工具栏 8 图标、Tiptap 编辑器（StarterKit + tiptap-markdown + 自定义查找高亮 ProseMirror 插件）、右栏大纲、底部字数统计、查找替换面板、Notion 风"块添加"浮动按钮 + 块类型菜单、Notion 风视觉样式（浅灰侧栏/无边框图标按钮/圆角卡片弹窗）。

**踩过的坑**：
1. Svelte 5 编译器禁止变量名以 `$` 开头（与 rune 语法冲突），ProseMirror 惯用的解构写法 `const { $from } = selection` 在 `.svelte` 文件里会编译报错 `dollar_prefix_invalid`，需重命名为 `const { $from: sel } = selection`。
2. `npm install` 因 `allow-scripts` 策略拦截了 `esbuild` 的 postinstall（原生二进制下载脚本），需要在 `package.json` 显式加回 `"allowScripts": { "esbuild@<版本>": true }`（版本号需对应 `npm install` 实际解析出的 esbuild 版本，随依赖更新可能变化）。
3. **截图验证时的 DPI 虚拟化坑**：本机系统缩放 150%。用非 DPI-aware 的 PowerShell 进程调用 `GetClientRect`/`PrintWindow` 截取一个已声明 per-monitor-v2 DPI-aware 的窗口（Wails 默认生成的 manifest 已声明），会拿到被虚拟化缩小的窗口尺寸，导致 `PrintWindow` 只截到左上角一部分，右侧大纲栏、底部状态栏"看起来没渲染"——其实是截图脚本的坐标系问题，不是应用 bug。修复：截图前对当前线程调用 `SetThreadDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`（值 `-4`），再读 `GetClientRect`/`PrintWindow` 即可拿到真实物理像素尺寸和完整内容。**后续任何要截图验证 Wails/WebView2 窗口的场景都应先设置这个 DPI 上下文，否则会得出"某块 UI 没渲染"的假阴性结论。**
4. `SetForegroundWindow` / `WScript.Shell.AppActivate` 在自动化环境里可能静默失败（Windows 焦点抢占保护），此时对目标 hwnd 截图可能实际截到桌面上其它无关窗口的内容而不报错——因此窗口截图一律优先用 `PrintWindow`（直接从窗口自身取内容，不依赖前台焦点/坐标是否被其它窗口遮挡），比"前置窗口 + 截屏"更可靠。
5. 测试中发现一次 `build\bin\data\settings.json` 出现了非预期的 `rootDir`（指向一个真实存在的用户目录），具体触发路径未完全定位（怀疑与前几次窗口激活尝试有关），但确认代码里没有任何写死的默认路径、也没有自动写入逻辑。每次测试后已手动清空 `build\bin\data`；如后续复现，需要重点排查 `runtime.OpenDirectoryDialog` 在窗口未正确获得前台焦点时是否会静默返回系统缓存的"上次选择目录"而不是真正弹窗等待用户选择。

**产物**：`wails build -clean -ldflags "-s -w"` → `build\bin\mdnote.exe`，约 11.4MB（未装 `upx.exe`，未做进一步压缩）。已实机启动 + `PrintWindow`（DPI-aware）截图确认：目录空态、标签栏（已移到最上方）+ 工具栏（已移到标签栏下方）、大纲栏、状态栏、编辑区"块添加"浮动按钮均正常渲染。

## 2026-07-23（续）：用户测试第一轮反馈的 6 个 bug 修复

1. **新建空文件夹在左栏不显示、刷新无效**：根因是 markdown-only 过滤规则本身——"目录不含 md 递归子项就隐藏"对刚创建的空文件夹同样成立，所以新建出来的空文件夹立刻被过滤掉；刷新按钮其实工作正常，只是重新算出了同样的过滤结果。修复：`fsops.go` 新增 `shouldShowDir`，目录为"真正空"（一个子项都没有）时也展示，不再要求必须已含 `.md`。
2. **悬浮"+"点了没弹出菜单**：块菜单按钮/菜单项都在 ProseMirror 的 contenteditable 区域之外，点击时浏览器先在 `mousedown` 阶段把编辑器 blur 掉，而 `onBlur` 回调里 `if (!menuOpen) handleTop = null` 判断的是"blur 发生那一刻"的 `menuOpen`（此时点击的 `onclick` 还没来得及把它设成 true），于是按钮和菜单在真正触发点击前就被判定为要隐藏。修复：给按钮和每个菜单项加 `onmousedown` 里 `preventDefault()`，阻止这次点击引发编辑器失焦。
3. **新增：光标所在空行显示浅色提示"按 / 或空格快速插入格式"**：直接使用 `@tiptap/extensions` 里官方的 `Placeholder` 扩展（默认 `showOnlyCurrent: true`，正好只在当前光标所在空行显示），加了对应 `.is-empty::before` 样式。
4. **redo 无内容时应置灰**：`editorBridge` 新增 `canUndo`/`canRedo` 两个响应式字段，编辑器每次 `onTransaction` 都调用 `editor.can().undo()/.redo()` 同步；工具栏按钮据此加 `disabled`。
5. **撤销把所有内容一次性撤没**：定位到真实 bug——`editor.commands.setContent(content, false)` 里第二个参数在当前 Tiptap 版本已经是"选项对象"而不是布尔值（`{ emitUpdate = true, ... } = {}` 解构），传 `false` 进去完全不生效、`emitUpdate` 仍按默认 `true` 处理；更关键的是这次内容替换的事务从未打上 `addToHistory:false`，导致每次切换标签页/打开文件，都会把"整篇替换"当一步推进撤销历史——只要用户后续撤销几次就会命中这一步，表现为"内容整体消失"。修复为 `editor.chain().setMeta("addToHistory", false).setContent(content, { emitUpdate: false }).run()`，正确使用选项对象且不再污染撤销历史。未改动默认 500ms 的按键分组间隔（`newGroupDelay`）——这是几乎所有编辑器的标准行为（连续快速输入算一步撤销），如果用户验证后仍觉得需要"每个字符单独一步撤销"，需要再单独调整。
6. **关闭未保存标签的"不保存"按钮改名"舍弃"+红色**：`ConfirmDialog.svelte` 按钮文案改为"舍弃"，加 `class="danger"`（复用删除确认已有的红色样式）。

修复后已 `wails build -clean -ldflags "-s -w"` 重新产出 `mdnote.exe`（约 11.4MB）并截图确认：占位提示文本、撤销/重做置灰态均正常渲染。

用户测试反馈 8 个问题，逐一定位修复：

1. **打开 md 文件后窗口取消最大化**：根因是应用从未记住过窗口的最大化状态——`main.go` 里 `WindowStartState` 一直没设置，每次启动/新开窗口都固定用默认的 1280×800，用户之前手动最大化过也不会被记住。修复：`settings.go` 的 `Settings` 加 `WindowMaximized` 字段（ini 里 `Maximized=` 键），`app.go` 新增 `onBeforeClose`（关闭前用 `runtime.WindowIsMaximised` 读取当前状态存盘），`main.go` 启动时读取该值决定 `WindowStartState` 是否为 `options.Maximised`。`SelectRootDir` 原来存盘时是 `Settings{RootDir: dir}` 直接覆盖整个结构体，会把 `WindowMaximized` 一起清零，顺手改成先 `loadSettings()` 再只改 `RootDir` 字段。已实机验证：ini 里手写 `Maximized=true` 启动后 `IsZoomed` 为真；取消最大化后关闭，ini 自动写回 `Maximized=false`。
2. **打开文件后未修改也显示脏点**：根因是 `Editor.svelte` 的 `syncFromEditor()` 在"刚加载/切换标签"时也会被调用，它会把 `tiptap-markdown` 重新序列化出的 markdown 写回 `tab.content`——而这个"编辑器→markdown"往返序列化不保证和原始文件字节完全一致（列表符号、标题写法、尾随换行等归一化），于是 `tab.content` 和 `tab.savedContent`（原始文件内容）出现细微差异，被判定为"脏"。修复：拆出一个只刷新大纲/字数、不touch `tab.content` 的 `refreshDerivedState()`，加载/切换标签时改调它；只有真正的用户编辑（`onUpdate`）才会调用会重写 `tab.content` 的完整 `syncFromEditor()`。
3. **新增：双击标签重命名**：`Tabs.svelte` 加 `renamingId`/`renameValue` 状态，双击标签标题进入编辑；未命名过的空白标签（仍是默认"未命名.md"）→ 输入框留空聚焦；已有实际名字（真实文件，或之前改过名的空白标签）→ 全选文字方便直接覆盖。有 `path` 的标签提交时走 `appState.renameEntry`（真正改磁盘文件名，和左栏重命名同一套逻辑，保持标签与文件同步）；没有 `path` 的未保存标签只改内存里的 `tab.title`——由于"另存为"早就用 `tab.title` 当默认文件名（见上一轮"根目录默认目录"那次改动），改完标题后另存为自动就会用新名字。
4. **标签拖拽只能左移到第一个，不能右移到最后一个**：原生 HTML5 拖拽的 `ondragover`/`ondrop` 都绑在具体的标签按钮上，最后一个标签右侧的空白区域没有任何元素能接住 drop，所以"拖到最后"这个手势没有落点。修复：`.tabs-scroll` 末尾加一个 `flex:1` 的占位 `div` 承接 dragover/drop，触发 `appState.moveTabToEnd`。（顺带发现 Tabs.svelte 是唯一还在用原生 HTML5 DnD 的地方——和之前判定"WebView2 原生拖拽事件完全不触发"不同，这里显然是能收到事件的，只是缺少末尾落点；说明那条结论对标签栏不成立，具体原因未深究，但既然现状可用就不再额外改造成指针事件。）

修复过程中还发现一个连带 bug：给 `Tabs.svelte` 加 `$state` 用于重命名功能后，组件整体切换到 Svelte 5 runes 模式，暴露出原来 `draggingId`/`dragOverId` 是普通 `let`（非 `$state`）——在 legacy 模式下这类顶层变量隐式响应式，一旦文件因为其它 `$state` 用法被强制转成 runes 模式，普通 `let` 的重新赋值就不再触发界面更新了（`svelte-check` 报 `non_reactive_update` 警告）。顺手把这两个变量也改成了 `$state`，避免标签拖拽的高亮/占位反馈静默失效。

## 2026-07-24：块拖拽 bug 根因定位 + 文件夹重命名报错 toast

用户反馈"内容区域/内容块还是无法实现拖拽移动"——上一轮虽然把块拖拽从原生 HTML5 DnD 改成了指针事件（能触发了），但读取 `DebugLog` 上一次实机测试留下的 `build\bin\debug.log` 发现移动过程中 `updateDropTarget` 里的 `editor.view.posAtCoords` **每一次 pointermove 都返回 null**，导致 `dropTargetPos` 永远是 null、`commitBlockMove` 永远拿不到落点，拖拽等于什么都没发生。

**根因**：查了 `prosemirror-view` 源码（`posAtCoords` 实现），坐标一旦落在 `view.dom.getBoundingClientRect()`（即 `.tiptap` contenteditable 元素自身的渲染框）之外就直接返回 null。而 `.tiptap` 的高度只等于其实际内容高度，外层 `.editor-content-col-wrapper` 却为了"点击末尾空白也能落光标"这个体验特意留了 `padding: 56px 64px 30vh`——只要拖拽时鼠标移到最后一行下方（或短文档场景下很容易发生），坐标就落在这段空白 padding 里，落在 `.tiptap` 框外，`posAtCoords` 必然返回 null。侧栏文件树的拖拽用的是 `document.elementFromPoint`（永远能命中点什么，包括空白容器），所以那条路没有这个问题；块拖拽换成指针事件后事件本身能触发了，但命中测试用的是 ProseMirror 自己的 `posAtCoords`，这个函数的"越界即 null"特性在上一轮改造时没被注意到，是两条拖拽实现路径行为不一致的根本原因。

**修复**：`Editor.svelte` 的 `updateDropTarget` 在调用 `posAtCoords` 前，先把 `clientX/clientY` 钳制（clamp）到 `editor.view.dom.getBoundingClientRect()` 内侧 1px，这样拖到内容下方/左右留白时会落到最近的真实文档位置而不是直接判 null。诊断用完后清理了 `DebugLog`（`app.go`）、`api.debugLog`（`api.ts`）、`Editor.svelte` 里的埋点调用，以及 `build\bin\debug.log`。

同一轮用户还反馈"重命名文件夹时，名字改成功了，但底部还是弹错误 toast"。定位：`TreeNode.svelte` 的 `commitRename` 挂在 `<input>` 的 `onkeydown`（Enter）和 `onblur` 两处；按 Enter 时 `commitRename()` 把 `renaming` 置 false，`{#if renaming}` 块随之把这个仍处于聚焦状态的 `<input>` 从 DOM 里摘掉——原生浏览器行为是"聚焦元素被移除会触发一次 blur"，于是 `onblur` 又把 `commitRename()` 调用了第二次。第二次调用时 `entry.path`/`entry.name` 还是重命名前的旧值（父组件的 children 列表要等 `refreshTree()` 异步回来才会用新 path 替换这个节点），于是又拿着已经被改名、此刻已不存在的旧路径发起一次 `RenameEntry`，必然失败，弹出"重命名失败"toast——尽管第一次调用早已成功、UI 上名字也确实改对了。`Tabs.svelte`（标签重命名）和 `NewEntryRow.svelte`（新建文件/文件夹）本来就各自有 `renamingId !== tab.id` / `settled` 这种"重入拦截"，唯独 `TreeNode.svelte` 没加，属于三处本该一致的模式里漏了一处。修复：`commitRename` 开头加 `if (!renaming) return;`，与另外两处的写法保持一致。

`go build`、`npm run check` 均 0 错误，`wails build -ldflags "-s -w" -o mdnote2.exe` 重新产出（`mdnote.exe` 当时正被用户实机运行占用，改产出到 `mdnote2.exe`）。两处改动都需要真实鼠标交互才能验证效果，建议用户直接用 `mdnote2.exe` 实机测试：1）多块文档里用六点手柄把某个块拖到另一个块的上/下方，包括拖到文档最后一块下方的空白区域；2）右键文件夹重命名，确认改名后不再弹"重命名失败"。

## 2026-07-26（第六轮）：页面/文件链接改成基于 id 的稳定引用

用户反馈：上一轮的 `syncLinkReferences` 只能修到"重命名发生时正好开着"的标签页——如果链接所在的文件当时是关闭的，它保存在磁盘上的 `path` 就一直是旧的，之后重新打开这篇文件，链接照样是坏的。用户明确要求"记录 2 个文件的 id 关系"，即用一个不随文件改名/移动而变化的稳定 id 做间接引用，而不是直接存路径。

## 2026-07-26（第七轮）：找到 pageLink/fileLink 芯片"变身普通链接"的真正根因——一个远早于这次会话就存在的 parseHTML 优先级 bug

用户反馈：新建文件链接、跳转到新文件、改名、回原文件——芯片显示名没跟着更新，而且**芯片本身变成了"链接格式"**（普通蓝色下划线超链接，不再是带图标的胶囊）。

上一轮的 id 机制理论上能解决"改名时文件关着"这种场景，但这次报告的现象更基础：芯片**从 `pageLink`/`fileLink` 节点整个退化成了 StarterKit 自带的 Link *mark***——一旦退化，`path`/`id` 属性全部丢失，`syncLinkReferences`/`LinkClickHandler` 里所有认 `node.type.name==="pageLink"` 的逻辑自然全部失效（既不会被同步更新，点击也不会走内部跳转——退化后的元素还带着 `link-chip` 这个 class，而 `LinkClickHandler` 里处理普通超链接的那段代码又特意排除了 `classList.contains("link-chip")` 的元素，两头都够不着，等于彻底点不动）。

**没法靠读代码猜出根因，直接写了一个 Node.js 脚本用真实的 `@tiptap/core`/`tiptap-markdown` 库复现"编辑器→ markdown 字符串 → 重新解析回编辑器"这个往返**（临时装了 `jsdom`——`tiptap-markdown` 的 HTML 兜底解析需要 `window.DOMParser`，`npm install --no-save` 避免污染 `package.json`；用完 `npm uninstall` 卸载干净，`git status` 确认没有留痕）：一个内容为纯文本 + `pageLink` 芯片的段落，序列化成 markdown 字符串（能看到正确的 `data-path`/`data-id`/`data-type="page-link"` 都在），但**重新解析回去之后，`doc.descendants` 里完全找不到 `pageLink` 节点，芯片的文字变成了带 `link` mark 的纯文本**——和用户描述的现象完全对上。

**根因**：`links.ts` 的 `pageLink`/`fileLink` 节点 `parseHTML()` 只给了 `{tag: 'a[data-type="page-link"]'}`，没写 `priority`。StarterKit 自带的 Link *mark* 同样能匹配任意 `<a href="...">` 标签，两条规则应对同一个 `<a>` 元素，ProseMirror 的 `DOMParser` 按优先级（默认都是 50，相同优先级下顺序不保证由"谁在扩展列表里注册得晚"决定）二选一——结果证明 Link mark 赢了，pageLink/fileLink 节点从来没有真正生效过。这个 bug 和这次会话的任何改动都无关，**从这两个节点第一次写出来那天就存在**：只要文档经历过一次"编辑器内容→markdown 字符串→重新解析回编辑器"的往返（包括切标签页——每次切换都会把 `tab.content` 重新 `setContent` 一遍，不需要真的保存/重开文件），芯片就会退化成死链接。之前几轮截图看起来"渲染正常"，是因为测试用的文件从没经历过这个往返（要么是刚创建就截图，要么是第一次加载，还没有被"切一次标签页"这个动作污染过）。

**修复**：`parseHTML()` 显式给 `priority: 100`（高于默认 50），确保 pageLink/fileLink 节点的匹配规则在 Link mark 之前生效。用同一个 Node 脚本验证：加上 `priority` 后，往返解析正确保留 `pageLink` 节点及其 `path`/`id` 属性；连着"改名后 `syncLinkReferences` 的字符串替换 + 重新解析"这一整条链路也一并跑通了（替换后的 `data-path` 正确出现在重新解析出的节点属性里）。

`npm run check`（241 文件 0 错误）通过，`wails build` 重新产出后实机加载一份含手写芯片的测试文件确认初次渲染仍然正常（这次修复没有破坏"第一次打开就显示正确"这条已经在工作的路径）。这是这次改动里少数**能被相对严格验证**的一处——不是靠截图肉眼看，而是直接用真实序列化/解析代码跑出了"改之前必现、改之后消失"的对照结果，置信度明显高于前几轮的静态截图检查。`wails build -ldflags "-s -w" -o MDNote.exe` 重新产出，全程未触碰用户真实 `mdnote.ini`。

## 2026-07-26（第十一轮）：侧边栏双击改名、同目录拖拽误报、图标替换、Tab 拖拽方向 bug、列表内拖拽排查

用户这轮反馈 5 点，逐项处理：

1. **左侧栏双击文件夹/文件进入改名状态**：`TreeNode.svelte` 新增 `onRowDblClick`（`ondblclick` 挂到行上），直接复用已有的 `startRename()`——和右键菜单"重命名"走同一套逻辑，没有新增状态。双击时原生事件顺序是 click→click→dblclick，`onRowClick` 会先跑两次（文件夹会展开又收起，文件会打开两次，都是幂等操作），dblclick 才触发改名，和 VS Code 一类编辑器的常见手感一致。

2. **同目录内拖拽（含拖到根目录）弹"移动失败"误报**：根因是两处路径表示不一致——`dragController.ts` 里根目录的拖放目标 `appState.effectiveRootDir` 是前端用字符串拼接 `${rootDir}\\MDNote` 算出来的，没有走 Go 的 `filepath.Join`/`filepath.Clean`；而兄弟行的目标路径是后端 `ListDir` 返回的、已经规整过的路径。两者只要在大小写或尾部分隔符上有一点差异，`dragController.ts` 里"目标和当前所在目录相同就不发请求"的客户端守卫就会误判成"不同目录"，实际发去的 `MoveEntry` 落到后端自己的"已在目标目录中"校验上，报错文本原样弹成 toast。修了两处：`dragController.ts` 加 `normPath()`（小写化 + 去掉尾部分隔符）后再比较；`appState.moveEntry` 的 catch 里额外识别这句错误文本，命中就静默返回，不弹 toast——这个错误本质是"不需要移动"，不是真失败，只有其它真错误才继续弹。

3. **应用图标换成 `build/icon.png`**：Wails 的图标生成约定死认 `build/appicon.png` 这个文件名，且只在 `build/windows/icon.ico` 不存在时才会重新生成——项目原来就有一份旧 `icon.ico`，光换 `appicon.png` 不会自动生效。把 `icon.png` 复制成 `appicon.png`，删掉旧的 `icon.ico`，`wails build` 时被动重新生成，新图标才真正编译进 exe。

4. **Tab 栏拖拽方向性 bug（左边 tab 拖到右边不生效，反过来可以）**：`appState.svelte.ts` 的 `reorderTab(fromId, toId)` 是经典的"先删后插"位置计算错误——`splice(fromIdx,1)` 删除源位置后，数组里排在源后面的所有元素下标都会整体减一，但代码直接拿删除前的 `toIdx` 去 `splice` 插入，没有针对"目标本来在源后面"这种情况做下标修正，导致目标偏移比预期的落点靠后一位（插到了目标之后，而不是拖拽指示线画的目标之前）；目标本来在源前面时因为下标没受影响，插入位置反而歪打正着是对的——这就是"左拖右坏、右拖左好"这个方向性差异的完整成因。修法：`fromIdx < toIdx` 时插入下标额外 `-1` 补偿，两个方向都会精确落在指示线标出的位置。

5. **列表内部拖拽重排（编号列表/子弹列表内把一行拖到另一行位置）反馈"完全没有插入提示线"**：这是本轮排查耗时最长的一点。`Editor.svelte` 的 `updateDropTarget`/`effectiveBlockPos`/`commitBlockMove` 逐行读下来，逻辑设计上就是按 `listItem` 粒度独立寻址每一行（历史上第五/九/十轮专门做过这件事），静态审查找不出会导致"同一个列表内目标恒等于源"的路径。因为本环境没法用鼠标做真实拖拽手势，这次没有停留在"读代码觉得没问题"就了事，而是搭了两层真实浏览器验证（`npm run dev` 起 Vite 开发服务器 + 临时装 `playwright`（用完卸载，`git status` 确认无残留）驱动真实 Chromium）：第一层只抠出 `effectiveBlockPos` + 排除守卫这段核心算法单独跑，第二层直接挂载真实的 `Editor.svelte` 组件（塞一个内容为 3 项编号列表的假 tab 到 `appState.tabs`），用 Playwright 的 `page.mouse` 在真实坐标上做"悬停显出手柄→按住手柄→拖动→悬停另一行→松手"完整手势。两层测试里，编号列表和额外试的"先在页边距拖拽选中一段、不点回正文就直接抓另一行拖"（怀疑残留 `multiSelectRange` 导致粒度退化成整个列表）都完整复现了预期行为：指示线正确出现在悬停的每一行，松手后文档顺序也确实按预期重排。也就是说这套逻辑在真实 Chromium 里是对的，没有找到能让"同列表内无提示"必现的代码路径。已如实告知用户：不排除是 WebView2（Wails 桌面壳用的渲染引擎，和测试用的独立 Chromium 版本/实现细节不完全一致）某个特有的指针事件/坐标计算差异，需要用户在实际桌面应用里重新测试这次重新构建的 exe，并确认具体触发方式（是否通过悬停后出现的"⋮⋮"手柄拖动）、是否只在某些文档/列表长度下出现，才能进一步定位。

`npm run check`、`go build ./...` 均确认无误。第 1/2/4 点是有明确改动、逻辑可静态证明正确的修复；第 3 点图标替换直接验证产物里 `icon.ico` 已更新；第 5 点没有代码改动（没找到需要改的地方），已经过本环境能做到的最高强度验证（真实浏览器 + 真实指针事件 + 真实文档结构变化断言），但仍需用户在真实 exe 里复测确认。`wails build` 重新产出（这轮改动只涉及前端，`-ldflags "-s -w"` 精简参数这次没加，产物比历史版本略大但不影响功能），全程未触碰用户真实 `mdnote.ini`。
